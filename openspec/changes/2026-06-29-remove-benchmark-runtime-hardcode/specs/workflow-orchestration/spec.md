## ADDED Requirements

### Requirement: Runtime Workflow Orchestration Shall Be Benchmark Agnostic

Runtime workflow orchestration SHALL NOT encode benchmark-specific gates, budgets, prompt classifiers, profile ids, repository names, task ids, instance ids, expected patches, scorer behavior, or benchmark terminal reasons.

runtime workflow orchestration 不得编码 benchmark-specific gates、budgets、prompt classifiers、profile ids、repository names、task ids、instance ids、expected patches、scorer behavior 或 benchmark terminal reasons。

#### Scenario: Benchmark token rejected in runtime source

- **WHEN** architecture lint scans shared runtime or shared platform package source
- **AND** the source contains benchmark-specific tokens such as `SWE_BENCH`, `SweBench`, `sweBench`, `swe-bench`, or `swebench`
- **THEN** lint fails with a stable benchmark-boundary rule id
- **AND** the finding points the implementation toward host-owned evaluation adapters or dynamic profile data
- **中文** 当 architecture lint 扫描 shared runtime 或 shared platform package source，且源码包含 `SWE_BENCH`、`SweBench`、`sweBench`、`swe-bench` 或 `swebench` 等 benchmark-specific tokens 时，lint 必须用稳定 benchmark-boundary rule id 失败，并指向 host-owned evaluation adapters 或 dynamic profile data。

#### Scenario: Benchmark-like workflow uses generic staged controls

- **WHEN** a benchmark-like task is admitted for execution
- **THEN** runtime scheduling uses generic staged workflow controls such as ready-stage control, allowed tools, progress capability ids, workflow boundary guards, evidence-driven stage advancement, stage acceptance mode, and terminal close policy
- **AND** runtime does not branch on the benchmark family name or scorer-specific close condition
- **中文** 当 benchmark-like task 被准入执行时，runtime scheduling 必须使用 ready-stage control、allowed tools、progress capability ids、workflow boundary guards、evidence-driven stage advancement、stage acceptance mode 与 terminal close policy 等通用 staged workflow controls，且 runtime 不得基于 benchmark family name 或 scorer-specific close condition 分支。

### Requirement: Benchmark-Like Profiles Shall Be Dynamic Or External Data

Benchmark-like task profiles SHALL be generated by the model, loaded from an external profile artifact, or supplied by a host controller as declarative data. CLI/runtime SHALL load, validate, compile, and schedule those profiles through generic profile governance, but SHALL NOT hardcode a phase-1 benchmark profile as source-code behavior.

benchmark-like task profiles 必须由模型生成、从外部 profile artifact 加载，或由 host controller 以声明式数据提供。CLI/runtime 必须通过通用 profile governance 加载、校验、编译和调度这些 profiles，但不得把第一期 benchmark profile 作为源码行为 hardcode。

#### Scenario: Phase-1 profile cannot be embedded in CLI or runtime code

- **WHEN** CLI/runtime prepares a benchmark-like staged workflow
- **THEN** any benchmark-like stage order, allowed tools, budgets, acceptance gates, and terminal policies come from dynamic or external profile data
- **AND** source code only applies generic profile admission, compilation, and scheduling rules
- **中文** 当 CLI/runtime 准备 benchmark-like staged workflow 时，任何 benchmark-like stage order、allowed tools、budgets、acceptance gates 与 terminal policies 都必须来自 dynamic 或外部 profile data；源码只应用通用 profile admission、compilation 与 scheduling rules。
